One C++ core, shipped as WebAssembly instead of a .so Um núcleo C++, empacotado como WebAssembly em vez de .so

A proof of concept on portability, fault containment and hot updates. Uma prova de conceito sobre portabilidade, contenção de falhas e atualização a quente.

calc.cpp → libcalc.so × 4 vs calc.wasm × 1

Today we package our C++ as native .so libraries. In this POC I took one small C++ function and packaged it two ways, from the same source and the same compiler: as a .so called through JNI, and as a WebAssembly module running inside the JVM.

I want to show three things in about seven minutes. First, and most important, portability: one binary instead of one per CPU. Second, what happens when the C++ crashes. Third, updating the C++ without shipping a new app. Then the pros and cons, because this is not free.

Hoje a gente empacota nosso C++ como bibliotecas nativas .so. Nesta POC eu peguei uma função C++ pequena e empacotei de dois jeitos, a partir do mesmo código e do mesmo compilador: como um .so chamado via JNI, e como um módulo WebAssembly rodando dentro da JVM.

Quero mostrar três coisas em uns sete minutos. Primeiro, e mais importante, portabilidade: um binário só, em vez de um por CPU. Segundo, o que acontece quando o C++ quebra. Terceiro, atualizar o C++ sem publicar um app novo. Depois, prós e contras, porque isso não sai de graça.

How we ship C++ today: one .so per CPU Como entregamos C++ hoje: um .so por CPU

  • One binary per ABI, per platformUm binário por ABI, por plataforma
  • Each new target brings its own toolchain to build and testCada novo alvo traz seu próprio toolchain para compilar e testar
  • Frozen in the APK: a change needs a new build and a store reviewCongelado no APK: mudar exige build novo e revisão da loja
  • A native fault kills the whole processUma falha nativa derruba o processo inteiro

This is the native path. The C++ is compiled to machine code, so we need one .so for every CPU architecture we support. On Android that is four ABIs. Add iOS, desktop or a server, and each one brings its own toolchain and its own binary to build, test and keep in sync.

That binary is frozen inside the APK. To change one line of C++ we need a new app build and a new store review. And because it is real machine code running inside our process, when it faults, the operating system kills the whole app.

Keep these four points in mind. The rest of the talk goes through them one by one.

Esse é o caminho nativo. O C++ vira código de máquina, então a gente precisa de um .so para cada arquitetura de CPU que suporta. No Android são quatro ABIs. Some iOS, desktop ou servidor, e cada um traz seu próprio toolchain e seu próprio binário para compilar, testar e manter em sincronia.

Esse binário fica congelado dentro do APK. Para mudar uma linha de C++ a gente precisa de um build novo do app e de uma nova revisão da loja. E como é código de máquina de verdade rodando dentro do nosso processo, quando ele falha, o sistema operacional mata o app inteiro.

The experiment is deliberately tiny: one C++ file with one function, calc_divide. The interesting part is the build. Both outputs come from the same file and the same compiler. The Android NDK's clang already ships a wasm32 backend, so we didn't install emscripten or wasi-sdk.

On the left, CMake builds the .so once for every ABI. On the right, one clang command with --target=wasm32 produces a single calc.wasm. No libc, no entry point, so the module needs nothing from the host.

We also freeze the contract: double calc_divide(int, int). The app binds to that signature, and only the body changes between versions. That is what makes the hot update possible later.

A gente também congela o contrato: double calc_divide(int, int). O app se liga a essa assinatura, e só o corpo muda entre versões. É isso que torna possível a atualização a quente mais adiante.

The main pointO ponto principal ≈ 1:10

Portability: one binary, the same behavior on every CPU Portabilidade: um binário, o mesmo comportamento em qualquer CPU

  • Wasm is bytecode: the runtime deals with the CPU, not usWasm é bytecode: o runtime cuida da CPU, não a gente
  • Chicory is pure Java: no native code on this path at allChicory é Java puro: nenhum código nativo nesse caminho
  • Edge cases are defined by the spec, not by the hardwareCasos de borda são definidos pela spec, não pelo hardware
  • Same file could serve backend or iOS with another runtime (untested)O mesmo arquivo poderia servir backend ou iOS com outro runtime (não testado)

This is the main point. A .wasm file is not machine code, it is portable bytecode, and the runtime takes care of the CPU. Here the runtime is Chicory, which is written in pure Java, so there is no native code anywhere on the wasm path. One file serves arm64, x86 and whatever comes next.

It is not only about the file, it is about behavior. Look at the table. Integer division by zero in native C++ is undefined, and the hardware disagrees: on ARM64 it silently returns zero, on x86 it raises a signal and the process dies. In WebAssembly the spec defines it: it traps, on every host, the same way.

That is why the POC uses __builtin_trap: it was the only way to make the native side fail the same way on every phone. With wasm we get that consistency for free. In principle the same calc.wasm could also run on our backend, or on iOS with a different runtime. I haven't tested that part yet.

Esse é o ponto principal. Um arquivo .wasm não é código de máquina, é bytecode portável, e quem cuida da CPU é o runtime. Aqui o runtime é o Chicory, escrito em Java puro, então não existe código nativo em nenhum ponto do caminho wasm. Um arquivo só atende arm64, x86 e o que vier depois.

E não é só o arquivo, é o comportamento. Olhem a tabela. Divisão inteira por zero em C++ nativo é comportamento indefinido, e o hardware discorda: no ARM64 ela retorna zero em silêncio, no x86 ela dispara um sinal e o processo morre. No WebAssembly a spec define: dá trap, em qualquer host, do mesmo jeito.

Por isso a POC usa __builtin_trap: foi o único jeito de fazer o lado nativo falhar igual em todo celular. Com wasm essa consistência vem de graça. Em princípio, o mesmo calc.wasm também poderia rodar no nosso backend, ou no iOS com outro runtime. Essa parte eu ainda não testei.

Calling itChamando ≈ 0:45

From Kotlin, both look like a plain object No Kotlin, os dois parecem um objeto comum

From the app's point of view both transports look alike. On the left, JNI: System.loadLibrary, an external function, and a C++ wrapper whose name has to match the Kotlin package exactly.

On the right, wasm. init reads calc.wasm from the APK assets as a plain byte array, and load parses those bytes, builds an instance and looks up the export by name. One detail: Chicory returns values as raw 64-bit words, so we convert the bits back to a double.

Both sit behind a small Kotlin object, and the UI just calls divide. Notice that the wasm side takes bytes. Where those bytes come from is up to us: the APK assets today, a download tomorrow.

Do ponto de vista do app, os dois transportes são parecidos. À esquerda, JNI: System.loadLibrary, uma função external e um wrapper C++ cujo nome precisa bater exatamente com o pacote Kotlin.

À direita, wasm. O init lê o calc.wasm dos assets do APK como um array de bytes comum, e o load faz o parse desses bytes, cria uma instância e busca o export pelo nome. Um detalhe: o Chicory devolve os valores como palavras cruas de 64 bits, então a gente converte os bits de volta para double.

Os dois ficam atrás de um objeto Kotlin pequeno, e a UI só chama divide. Reparem que o lado wasm recebe bytes. De onde esses bytes vêm é escolha nossa: dos assets do APK hoje, de um download amanhã.

Calling backChamando de volta ≈ 0:55

Both can call Android. Only the .so can do it on its own. Os dois chamam o Android. Só o .so faz isso por conta própria.

A question that always comes up: can the C++ call back into Android? Yes, in both cases, but in different ways. The callback here is a plain Android toast, so you can see it is really native Android code running.

With JNI, the C++ gets a JNIEnv, looks up a Kotlin method by name and signature, and calls it. It can do that at any moment: it can start its own thread and call Android whenever it wants.

With wasm, the module declares an import, android.toast, and we hand it the implementation when we instantiate it. A string can't cross directly, so the C++ passes a pointer and a length, and Kotlin reads the text from the module's memory.

Two differences matter. The module can only call what we import, nothing else. And it can only call us while we are calling it, because it has no threads or timers of its own. If we need events, Kotlin calls a tick export and the C++ answers there.

Uma pergunta que sempre aparece: o C++ consegue chamar o Android de volta? Sim, nos dois casos, mas de jeitos diferentes. O callback aqui é um toast comum do Android, para ficar claro que é código Android nativo rodando.

Com JNI, o C++ recebe um JNIEnv, procura um método Kotlin pelo nome e pela assinatura, e chama. Ele pode fazer isso a qualquer momento: pode criar a própria thread e chamar o Android quando quiser.

Com wasm, o módulo declara um import, android.toast, e a gente entrega a implementação na hora de instanciar. Uma string não atravessa direto, então o C++ passa um ponteiro e um tamanho, e o Kotlin lê o texto da memória do módulo.

Duas diferenças importam. O módulo só consegue chamar o que a gente importou, mais nada. E ele só chama a gente enquanto a gente está chamando ele, porque não tem threads nem timers próprios. Se precisarmos de eventos, o Kotlin chama um export tick e o C++ responde ali.

[ demo · 10 / 0 on WebAssembly, then on JNI ]

Now the demo. Same input, ten divided by zero, and the exact same try/catch around both calls. First WebAssembly: the result shows "erro", a toast shows the trap message, and the app keeps running.

Now JNI: the process dies. Logcat shows fatal signal 4, SIGILL, inside libcalc.so. The try/catch never had a chance, because the signal kills the process before any Kotlin code runs.

With wasm the fault stays inside the sandbox. The module can only read and write its own linear memory, so a bug in the C++ can't corrupt the rest of the app. For us, that means one bad input doesn't crash the app in the user's hands.

[ demo · app open at v0.1 · 10 / 4 on WebAssembly = 2 ]

Second demo. The app is open at version 0.1, and ten divided by four on wasm gives two, because it is integer division. I apply a one-line change: cast before dividing. I bump the version to 0.2 and push to master. GitHub Actions compiles calc.wasm and publishes a release.

Back in the app, which I did not restart, I press Submit on WebAssembly. It sees 0.2 and asks if I want to update. I say yes, it downloads the module, re-instantiates it, and now the result is 2.5.

Pros and cons Prós e contras

So, pros and cons. On the plus side: one binary for every CPU, the same behavior on every host, crashes that stay contained, a sandbox that only sees what we hand it, updates without a store release, and we didn't even need a new toolchain.

On the other side, it is not free. Chicory interprets by default, so it is slower than native. It also has a compiler to JVM bytecode, but we still need to measure how that behaves on Android. The module has no direct access to the OS; this one has no libc at all. Passing anything more complex than numbers means copying data through the module's memory.

It is one more dependency in the app, and the debugging tools are behind the native ones. And downloading code means we need signing, plus a check against the Google Play and App Store rules.

Então, prós e contras. Do lado bom: um binário para qualquer CPU, o mesmo comportamento em qualquer host, crashes que ficam contidos, uma sandbox que só enxerga o que a gente entrega, atualização sem release na loja, e nem precisamos de um toolchain novo.

Do outro lado, não sai de graça. O Chicory interpreta por padrão, então é mais lento que nativo. Ele também tem um compilador para bytecode JVM, mas ainda precisamos medir como isso se comporta no Android. O módulo não tem acesso direto ao sistema; este aqui nem libc tem. Passar qualquer coisa mais complexa que números significa copiar dados pela memória do módulo.

É mais uma dependência no app, e as ferramentas de debug estão atrás das nativas. E baixar código significa que precisamos de assinatura, além de checar as regras do Google Play e da App Store.

Where it fitsOnde se encaixa ≈ 0:40

Not every .so, but self-contained logic Não todo .so, mas lógica autocontida

Pure C++ logic goes to wasm. Code that talks to the OS or needs every cycle stays native. Lógica C++ pura vai para wasm. Código que fala com o SO ou precisa de cada ciclo continua nativo.

To close: I'm not proposing to replace every .so. Code that talks to the OS, or needs every cycle of the CPU, should stay native. But self-contained logic, like rules, calculations and validation, is a good fit. We build it once, it runs the same everywhere, it can't take the app down, and we can fix it without a release.
